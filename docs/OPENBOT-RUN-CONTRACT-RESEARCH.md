# OpenBot run and completion contract

Source inspection only, pinned to OpenBot `ca8d51c3bf993e47e4d98a3c914a1958f1dafef0`, CopilotKit runtime `1.73.1`, and OpenBot's AG-UI client `0.0.59`. No headless OpenMuse-to-OpenBot run was performed.

## Supported flow

Use OpenBot's authenticated runtime route for the selected profile ID. Do not call a built-in Bot container directly: OpenBot constructs the runtime agents per actor, attaches their granted tools and policy context, and mounts the runtime under `/api/copilotkit`. [Agent lookup](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/src/agents/routes.ts#L363-L373), [runtime construction and mount](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/src/copilot.ts#L2119-L2168), [route mount](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/src/app.ts#L1113-L1121)

1. `GET /api/agents` returns the caller-visible agent IDs. Create a channel with `POST /api/channels` and JSON `{ "agentIds": ["<agentId>"] }`. The authenticated response is `201 { channel: { id, agentIds, threadId, ... } }`. OpenBot persists a mapping between the actor, channel, and minted thread ID; channel creation itself does not create the upstream Intelligence thread. [Channel creation and thread mapping](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/src/channels/routes.ts#L258-L307), [POST route](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/src/channels/routes.ts#L1067-L1080)

2. Start the selected agent at `POST /api/copilotkit/agent/<url-encoded-agentId>/run`. The JSON body is AG-UI `RunAgentInput`; in the pinned `@ag-ui/client` dependency it requires `threadId`, `runId`, `state`, `messages`, `tools`, `context`, and `forwardedProps`. `parentRunId` and `resume` are optional. Supply the channel's `threadId`, a unique caller-generated `runId`, current message history plus the new user message, and empty values for unused fields. [OpenBot dependency pins](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/package.json#L14-L22), [AG-UI core 0.0.59 schema](https://unpkg.com/@ag-ui/core@0.0.59/dist/index.d.ts), [runtime route matcher](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/core/fetch-router.ts#L98-L129), [run input validation](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/handlers/shared/agent-utils.ts#L267-L285)

3. In Intelligence mode, a successful run request waits for runner startup, then answers with JSON `{ threadId, runId, joinToken, realtime: { clientUrl, topic } }`, where `topic` is `thread:<threadId>`. This is startup/connection metadata, not the completed answer or an SSE response. Persist the returned IDs against the OpenMuse task. The runtime locks the thread before startup and returns its canonical thread/run IDs. [Pinned run handler](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/handlers/intelligence/run.ts#L158-L176), [startup boundary and response](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/handlers/intelligence/run.ts#L378-L419)

4. Observe the separate realtime thread stream and correlate terminal events by both `threadId` and `runId`. AG-UI `RUN_FINISHED` carries those IDs, an optional `result`, and an optional outcome; `RUN_ERROR` is the failure terminal event. `result` is optional, so collect assistant text from message events or retrieve the transcript rather than assuming `RUN_FINISHED` contains the answer. [AG-UI core 0.0.59 event types](https://unpkg.com/@ag-ui/core@0.0.59/dist/index.d.ts), [CopilotKit runtime realtime metadata](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/handlers/intelligence/run.ts#L24-L35)

## Reconnect and recovery

`POST /api/copilotkit/agent/<agentId>/connect` accepts a valid `RunAgentInput` (plus optional `lastSeenEventId`). For an active run it returns `{ threadId, joinToken, realtime }`; if no active join exists it returns `204`. The Intelligence handler does not return a run ID or answer on connect, and it does not pass `lastSeenEventId` into its thread-connect operation. [Connect validation](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/handlers/shared/agent-utils.ts#L288-L315), [connect response](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/handlers/intelligence/connect.ts#L42-L72)

Recover durable messages with `GET /api/copilotkit/threads/<threadId>/messages?agentId=<agentId>`; the runtime returns `{ messages }`. OpenBot's own client joins first and then fetches this history. [History handler](https://github.com/CopilotKit/CopilotKit/blob/v1.73.1/packages/runtime/src/v2/runtime/handlers/intelligence/threads.ts#L270-L289), [OpenBot client recovery order](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/app/src/components/channels/channel-chat.tsx#L338-L390), [OpenBot history request](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/app/src/lib/copilot/thread-messages.ts#L178-L200)

## Authentication and unverified work

With `OPENBOT_SINGLE_USER=true` and no identity provider, OpenBot assigns every request the fixed `dev-local-user` administrator; the runtime uses that same identity to scope Intelligence threads. A loopback headless caller therefore needs no browser cookie in this mode. This grants administrator access to every reachable caller, and OpenBot refuses this mode on public addresses. With an identity provider configured, the runtime requires an authorized signed-in user; its web client sends the Better Auth cookie with `credentials="include"`. No separate headless service-token contract is established by these sources. [Single-user actor](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/src/auth/dev-actor.ts#L24-L28), [runtime identity resolution](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/server/src/index.ts#L132-L162), [auth configuration](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/docs/configuration.md#L253-L294), [web cookie behavior](https://github.com/CopilotKit/OpenBot/blob/ca8d51c3bf993e47e4d98a3c914a1958f1dafef0/app/src/lib/copilot/provider.tsx#L18-L38)

The headless realtime join, terminal-event delivery, restart/reconnect race, and history consistency have not been exercised against a live deployment. The runtime source establishes the metadata and endpoint shapes, while OpenBot's web client uses CopilotKit's `connectAgent`; a headless integration still needs a live compatibility prototype for the realtime transport. No synchronous completed-answer API is present in the pinned run handler: it returns after startup, leaving completion to realtime events and history retrieval.
